## S4: follow-up subjects

Follow.cast accepts { WHO: '$WHO' } to bind the parent file's subject. Matching cast keys are also carried automatically if Follow.cast is omitted. An explicit map replaces that default, so supply all keys you want retained. Keys must be declared by the target event; parent tokens are checked by the linter.

Bindings are captured before outcome operations run, including a sack in that same decision. Person subjects also store the stable individual behind the legacy office key. The queued file and resulting desk item retain these bindings instead of selecting another person. Unbound roles can still use their selectors.

Policy for a departed or replaced holder: an office-dependent follow-up is withdrawn, with a consequence report, and never reassigned. If replacement happens while the follow-up is already on the desk, the file is resolved as withdrawn; its legacy effects cannot affect the new holder. This does not resolve or erase their requests, favours or commitments. A scene concerning a former holder in a new role still needs the R5 person/career API.

Old saves with unbound queue entries remain compatible; their original subjects cannot be reconstructed retrospectively. Current queue due dates remain presidency-relative; carrying whole episode queues across succession remains R2/calendar work.

## S6: scenario assets

engine/public.ts exports ScenarioAssets and StartingAssetSpec. Claude can import ScenarioAssets as a type into content/scenarios.ts and extend the Scenario interface with it, then add each dossier's matching assets entry:

    assets: [{ asset: 'wheat', site: 'KN', condition: 0.6 }]

newGame reads this optional field for a new world. Asset and site must exist and the site must be allowed by the asset definition. Duplicate asset IDs and non-finite or out-of-range conditions fail before any asset is added. Default condition is 1; the range is 0 to 1. Condition multiplies operating output, positive earnings and production records. Negative upkeep is still paid in full: poor condition does not waive maintenance. It is a fixed starting factor until a later maintenance/repair system changes it.

The existing career civil servant initially manages each inherited asset. The operating asset, site and asset flag exist; no new-president completion bonus, bet win, or invented historical production is awarded. An existing asset cannot be rebuilt by launching the same big bet; the existing expansion action remains available.

In a successor game, the outgoing world's assets take precedence over scenario templates. Condition, location, manager and production record carry over. Production records are deeply copied so advancing the successor does not mutate the outgoing save.

The API is delivered; the six existing scenarios have no assets field yet. Claude owns adding the declarations and numeric conditions consistent with the dossier prose. This delivery does not claim those worlds already start with the listed assets.
